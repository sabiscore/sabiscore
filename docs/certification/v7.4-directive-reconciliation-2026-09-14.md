## F1 — The "recovered contamination" premise is false. Classification: `NOT_JUSTIFIED` as stated.

**Draft claims:** v7.3's source document contained an embedded `<GenerateWidget>` tool-call block with a `widgetSpec` payload, plus ~2,500 words of raw Python (feature engineering, Redis sync, FastAPI auth), appended after `# END OF DIRECTIVE`. Removed and reorganized into a new Appendix A; §0.1 and INV-22 added to prevent recurrence.

**Evidence:** `docs/PRODUCTION_EXECUTIVE_DIRECTIVE.md` at HEAD is 710 lines, ends cleanly at `# END OF DIRECTIVE` (confirmed via direct read of the tail), with no appended content of any kind — no widget spec, no Python, nothing ungoverned.

**Finding:** The contamination the changelog describes fixing does not exist in the committed file. Whatever copy the v7.4 draft was written against, it was not this repository's `docs/PRODUCTION_EXECUTIVE_DIRECTIVE.md`. Two consequences:

1. **§0.1 (Document Integrity Rule) and INV-22 are still good additions on their own merits** — a real repo convention worth adopting regardless of what prompted them. Keep them.
2. **Appendix A is not "recovered" repository content — it is unverified, externally-authored code being proposed for the first time**, dressed as if it already had a history in this project. The draft's own §15.3.8 partially concedes this ("arrived as prose/chat output, not as verified repository content") but the top-level changelog still frames it as reorganization/cleanup rather than net-new. Treat Appendix A as a fresh proposal subject to full P1 §15.2 classification per file, same as any other unreviewed patch — not as governance archaeology.

Spot-checked the one concrete claim inside Appendix A that's checkable without the code itself: INV-24's motivating example (a hardcoded fallback credential defaulting when an env var is unset). `grep -riE "dev_fallback|fallback.*(key|token|secret)|CHANGE_IN_PROD" backend/src` returns exactly one match, and it's a feature-value fallback in `upcoming_match_feature_service.py`, unrelated to auth. **No such credential fallback exists in the current codebase.** INV-24 is a sound rule to adopt preventively; it is not correcting a live defect.

## F2 — Appendix C is real but six commits stale, and the staleness cuts the other way (good news, not bad).

**Draft claims:** `docs/certification/blocked-release-report-2026-09-14.md` (HOLD, HEAD `d20e2fa0`) is "the most recent real certification evidence for this repository."

**Evidence:**
- The file is real, committed at `c3c17f1` ("docs(certification): record v7.3 blocked release state", #188), and its content matches the draft's summary (HOLD; G11/G16/G18/G24/G27/G28 among the FAIL/UNVERIFIED rows; root defect: `SoftmaxMetaModel` inference reports `calibration_applied=True` when the label map says `"none"`).
- `d20e2fa0` is a real ancestor of current HEAD, **six commits back**: `c3c17f1` (the report itself) → `808a42e` (#189) → `3a06719` (#190) → `dcdcc69` (#191) → `a6a488a` (#192) → `53b7d1a` (#193, current HEAD).
- Commit `808a42e`, "fix(prediction): fail closed on calibration provenance" (#189), lands **one commit after** the report and is, on inspection of the actual diff, exactly the report's own required-exit-sequence steps 1–2:
  - `backend/src/models/prediction.py`: the unknown/uncalibrated meta-model fallback label changed from `"stacked_unknown"` to `"none"`, and `calibration_applied = True` (unconditional on a successful stacked prediction) changed to `calibration_applied = calibration_method != "none"`.
  - `backend/tests/test_prediction_engine.py` gained +71/−18 lines of regression coverage in the same commit.
  - This is precisely the G11/G27 FAIL condition the report names, fixed at the source it names.
- PR #191 (certification harness scripts — `evaluate_g11_ece.py`, `evaluate_g16_uncertainty.py`, `evaluate_g18_bootstrap.py`, `validate_deployment.py`, `compile_certification_report.py`) and #192/#193 (leakage-safe chronological feature engineering) landed after that fix, still unexecuted against current HEAD (per the "Sabi next steps" doc's own status: "local execution PENDING").

**Finding:** Appendix C's headline defect is fixed in source, one commit later, by the exact patch its own required-exit-sequence calls for. The draft doesn't know this because it's reconciling against a six-commit-old snapshot while treating that snapshot as current. This is not a case of "ignore stale data" — it's a case where citing the stale report *without* the six commits since it would make the release posture look worse (an unpatched calibration-mislabeling defect) than it actually is (patched, unverified). **Certification status is still correctly `HOLD`** — the report's own steps 3–6 (run tests, restore CI, re-run all gates against exact candidate SHA, regenerate the P18 report) have not happened; nothing here licenses `PROMOTE_RESEARCH_ONLY`. But "Appendix C, frozen at `d20e2fa0`" is the wrong artifact to canonicalize into a directive that's dated a day later. §32.3's proposal to canonicalize the blocked-release-report's gate-table *format* is fine; canonicalizing its specific *content* as current fact is the §1.2 historical-fact-rule violation the directive itself warns against.

**Action implied, not yet taken:** regenerate `blocked-release-report` (or run the compiled certificate) against HEAD `53b7d1a` before any directive cites a specific HOLD snapshot as current. That's an operator/execution decision (running `pytest`, the G11/G16/G18/G24 harnesses, `make verify`), not something to infer from git log alone — flagging it, not doing it here.

2. §0.1 / INV-22 (document-integrity rule) and INV-23 (dated-external-facts) are good, adoptable additions independent of the false premise — they don't need the contamination story to justify themselves.

Appendix A should be re-scoped from "recovered code" to "proposed code, unreviewed" and run through normal per-file P1 §15.2 classification before any of it lands — starting with the unsourced `OFFENSIVE_DISCOUNT=0.75`/`DEFENSIVE_PENALTY=1.30` constants the draft itself already flags as an INV-01 violation.
4. Before Appendix C is canonicalized anywhere, regenerate the certification report against current HEAD (`53b7d1a`) rather than freezing `d20e2fa0` — the picture has already changed for the better and a stale HOLD snapshot undersells it.
5. §15.3.7 needs its text updated to reflect resolution, not carried forward unchanged.
6. F3's Render free-tier finding is the one genuinely actionable, unresolved, real risk surfaced by this whole exercise — it's a legitimate OG-10 candidate independent of anything else in the v7.4 draft.
