# Notification channels — operator runbook

SabiScore delivers match alerts (kickoff reminders and probability-swing
alerts) over three channels. All three are generated by the same scheduled
worker, `backend/src/services/notification_dispatch_service.py`, which runs on
the FastAPI lifespan alongside fixture sync, settlement and CLV capture.

**Every channel writes an in-app row first.** `EMAIL` and `WEB_PUSH` are
best-effort *side effects* layered on top of it, counted but never able to
block or undo the log write. A transport outage therefore degrades to "the
notification is in the inbox but the push/email did not arrive", never to a
lost notification and never to a crashed dispatch pass.

| Channel | Transport | Enabled by | Default |
|---|---|---|---|
| `IN_APP` | Database row read by the notification centre | always on | on |
| `EMAIL` | `services/email_delivery.py` — stdlib `smtplib` | `ENABLE_EMAIL_NOTIFICATIONS` | **off** |
| `WEB_PUSH` | `services/web_push_delivery.py` — VAPID + RFC 8291 | `ENABLE_WEB_PUSH_NOTIFICATIONS` | **off** |

Both out-of-app channels are inert until an operator supplies credentials.
That is deliberate: an unconfigured channel reports its state
(`web_push_not_configured`, `email_not_configured`) in the dispatch counters
and in `GET /health` rather than raising.

## EMAIL

Any SMTP-speaking provider works (SES, Resend, Brevo, Postmark, Gmail) — there
is no vendor SDK and no vendor lock-in.

```env
ENABLE_EMAIL_NOTIFICATIONS=true
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_USERNAME=<username>
SMTP_PASSWORD=<password>
SMTP_FROM_ADDRESS=notifications@sabiscore.com
SMTP_USE_TLS=true
```

`SMTP_USERNAME`/`SMTP_PASSWORD` are optional — an unauthenticated relay skips
the login step. The channel reports itself unconfigured unless
`ENABLE_EMAIL_NOTIFICATIONS`, `SMTP_HOST` and `SMTP_FROM_ADDRESS` are all set.

## WEB_PUSH

### 1. Generate a VAPID keypair

```bash
npx web-push generate-vapid-keys
```

This emits a base64url public key and a base64url private key. Both are
accepted verbatim; a PEM private key is accepted too if you have one.

### 2. Configure the backend

```env
ENABLE_WEB_PUSH_NOTIFICATIONS=true
VAPID_PUBLIC_KEY=<public key>
VAPID_PRIVATE_KEY=<private key>
VAPID_CLAIMS_SUB=mailto:ops@sabiscore.com
WEB_PUSH_TTL_SECONDS=86400   # optional, defaults to 24h
```

`VAPID_CLAIMS_SUB` must be a `mailto:` or `https:` URI — push services use it
to contact you about a misbehaving sender, and some reject a token without it.

### 3. Nothing to configure on the frontend

There is deliberately **no `NEXT_PUBLIC_VAPID_PUBLIC_KEY`.** The browser reads
the key from `GET /api/notifications/push/public-key`, which proxies the
backend. The key is public by design (RFC 8292 §2), but serving it over the API
means rotating it is a backend restart rather than a frontend redeploy, and the
repo gains no new credential-shaped build variable.

While the channel is disabled the endpoint returns `configured: false` and the
browser never attempts a subscription it could not receive.

### 4. Verify

```bash
curl -s https://<backend>/api/v1/notifications/push/public-key
# {"configured":true,"public_key":"B..."}
```

Then, in the app: open any fixture, *Set alert* → **Push** → accept the browser
permission prompt. The dispatch counters in `GET /health`
(`components.notification_dispatch`) will start reporting `web_push_sent`.

### Rotating the keypair

Rotating invalidates every stored subscription — the push service rejects a
token signed by a key the subscription was not created with. After a rotation,
existing rows in `push_devices` will return `410 Gone`, and the worker
deactivates each one on its next attempt. Readers must re-enable push. Rotate
only when you have to.

## Operational notes

- **`push_devices` is transport, `user_notification_subscriptions` is intent.**
  One browser registration serves every match a reader subscribes to. The two
  tables are joined only at dispatch time, scoped strictly to the
  subscription's owner.
- **404/410 deactivates a device; 5xx does not.** A gone endpoint is
  permanent; a server error is the push service's problem and retrying is
  correct.
- **The service worker caches nothing.** `apps/web/public/sw.js` exists solely
  to receive push events. A caching worker on an evidence-gated product would
  be able to show a stale verdict, stale odds, or a stale evidence state with
  no indication it was stale.
- **CSP:** `worker-src 'self'` is set explicitly in
  `apps/web/src/middleware.ts`. It cannot be inherited — `worker-src` falls
  back to `script-src`, which carries `'strict-dynamic'`, and that neutralises
  `'self'`.

## Verification evidence

`backend/tests/unit/test_web_push_delivery.py` pins the encryption against
**RFC 8291 §5's published test vector, byte for byte**, and separately decrypts
a freshly generated payload the way a user agent would. This matters because
the failure mode is otherwise invisible: a push service accepts and forwards an
undecryptable body with a `201`, so a wrong key derivation would look like a
working feature that no browser ever displays.
